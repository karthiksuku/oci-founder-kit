# Golden path: full-stack app on OCI Container Instances

A web UI and API in one container, PostgreSQL, file uploads to Object
Storage, behind a load balancer, in a private network. It is the default
path in `oci-build` for a containerised web app that does not need
Kubernetes.

```text
client (allowed CIDRs) --HTTP--> Flexible Load Balancer (public subnet)
                                     |
                                     v  :8080, from the LB's NSG only
                            Container Instance (private subnet, fixed IP)
                              |                 |
                 :5432, NSG   v                 v  resource principal, PARs
          OCI Database with PostgreSQL      Object Storage bucket
```

## What it creates

| Area | Resources |
|---|---|
| Network | VCN; public and private subnets; internet, NAT and service gateways; an empty security list in place of the default one; network security groups for the load balancer, app and database |
| Compute | One OCI Container Instance (`CI.Standard.E4.Flex`) running `app/` with a fixed private IP |
| Data | OCI Database with PostgreSQL (TLS verified with the system's CA certificate); a private bucket |
| Access | A dynamic group for container instances in the compartment, and a policy limited to the app's bucket |
| Edge | A 10 Mbps flexible load balancer with an HTTP listener and a `/readyz` health check |
| Operations | A notification topic and an alarm for unhealthy backends |

## Choices you should know about

- **Ingress is closed by default.** `allowed_ingress_cidrs` has no default;
  only those ranges reach the load balancer.
- **HTTP only.** Add an HTTPS listener with a certificate from OCI
  Certificates, and a sign-in (OIDC with an OCI identity domain), before real
  users reach the app.
- **Sandbox secret handling.** The database password is generated by
  Terraform, kept in state, and passed to the container as an environment
  variable. For production, keep it in OCI Vault and read it at startup with
  the resource principal, and keep state in a remote backend.
- **One container instance.** Container Instances do not autoscale; for that,
  use the OKE path.
- **Teardown needs an empty bucket.** OCI does not delete a bucket that holds
  objects; empty it as part of the approved teardown.

## Run it

Everything goes through the approval gate in `skills/oci-deploy`.

```bash
cd app && npm ci && npm test                          # unit tests
docker build -t taskboard:0.1.0 app                    # image
# push to OCIR: <region-key>.ocir.io/<namespace>/taskboard:0.1.0

cp terraform/terraform.tfvars.example terraform/sandbox.tfvars   # fill in; ignored by Git
python3 ../../skills/oci-deploy/scripts/deploy_gate.py plan --dir terraform --var-file sandbox.tfvars
# show the summary to the owner; apply only with --approve <sha256> after approval
```

After the apply: open `app_url` from an allowed address, add a task, attach
a file, download it. `/readyz` reports the database.
