# Golden path: full-stack app on OCI Container Instances

A web UI and API in one container, PostgreSQL, file uploads to Object
Storage, behind a load balancer, in a private network. This is the default
`oci-build` path for a containerised web app that does not need Kubernetes.
An optional API Gateway entry point provides a managed HTTPS hostname for a
restricted rehearsal.

```text
client (allowed CIDRs) --HTTP sandbox / HTTPS hardened--> Load Balancer (default)
client (tester /32s)   --HTTPS hardened controls--------> API Gateway (optional)
                                     |
                                     v  :8080, from the selected ingress NSG only
                            Container Instance (private subnet, fixed IP)
                              |                 |
                 :5432, NSG   v                 v  resource principal
          OCI Database with PostgreSQL      Object Storage bucket
```

## What it creates

| Area | Resources |
|---|---|
| Network | VCN; private app/database subnet and a separate ingress subnet; internet, NAT and service gateways; an empty security list; network security groups for ingress, app and database |
| Compute | One OCI Container Instance (`CI.Standard.E4.Flex`) running `app/` with a fixed private IP |
| Data | OCI Database with PostgreSQL (TLS verified with the system's CA certificate); a private bucket |
| Access | A dynamic group for container instances in the compartment and access to the app's bucket; hardened mode adds reads of three selected Vault secrets |
| Edge | Default: 10 Mbps flexible load balancer, explicit sandbox HTTP or hardened HTTPS listener and `/readyz` health check. Optional: API Gateway with a managed HTTPS hostname and private app route |
| Operations | Load-balancer mode includes a notification topic and unhealthy-backend alarm; gateway mode needs its own reviewed operational checks |

## Choices you should know about

- **Ingress is closed by default.** `allowed_ingress_cidrs` has no default;
  only those ranges reach the entry point. Gateway rehearsal requires explicit
  tester IPv4 `/32` addresses.
- **Choose the operating mode.** The default is an unauthenticated, restricted
  HTTP sandbox. The [hardened reference](PRODUCTION.md) adds HTTPS, your chosen
  OIDC provider, per-user access, Vault secrets, backups and protected state.
  Verify those controls in your account before real users reach the app.
- **The optional gateway uses hardened app controls.** Set `ingress_mode =
  "api_gateway"` only with the [staged gateway procedure](PRODUCTION.md#optional-api-gateway-rehearsal).
  The gateway can be bootstrapped before its hostname is known; its application
  route requires complete OIDC/Vault configuration. Default managed certificates
  are for the restricted rehearsal, not a claim of production readiness.
- **Sandbox secret handling.** The database password is generated by
  Terraform, kept in state, and passed to the container as an environment
  variable. The hardened configuration uses an existing Vault secret version,
  reads it at startup with the resource principal and requires the documented
  remote-state setup.
- **One container instance.** Container Instances do not autoscale; for that,
  use the OKE path.
- **Teardown needs a retention decision.** Objects, versions and database backups
  require explicit inventory and approved cleanup; do not erase retained data
  merely to make a destroy command succeed.

## Run it

First use the [foundation workflow](../../skills/oci-foundation/SKILL.md).
The private `registry/` stack creates an empty image repository with
`immutable_tags = false`. Follow the
[digest publication gate](../../skills/oci-deploy/references/image-publication.md)
to prepare a private image layout, review the exact upload, and publish without
assigning a tag. Plan the app stack with the verified receipt's `@sha256:` URI.
Registry creation, image upload and application deployment have separate
approvals. Credentials and registry auth tokens stay outside Git. Live OCI
digest publication and the optional gateway flow still require account acceptance.

Everything goes through the approval gate in `skills/oci-deploy`.

```bash
npm --prefix app ci && npm --prefix app test           # unit tests, from this blueprint directory
docker build -t taskboard:local app                    # local tag only
# next: image-plan, owner approval, then image-push through oci-deploy

cp terraform/terraform.tfvars.example terraform/sandbox.tfvars   # fill in; ignored by Git
python3 ../../skills/oci-deploy/scripts/deploy_gate.py plan --dir terraform --var-file sandbox.tfvars
# show the summary to the owner; apply only with --approve <sha256> after approval
```

After the approved apply, verify `app_url` from an allowed address, add a task,
attach a file and download it. `/readyz` reports database readiness. The hardened
path also requires sign-in, two-user access checks and recovery acceptance.
The separate registry and retained images remain until cleanup is approved.
